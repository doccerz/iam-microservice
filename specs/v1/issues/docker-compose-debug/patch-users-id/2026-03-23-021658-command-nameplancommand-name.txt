  Step 2 & 3: Proposed Changes

  Only one addition is worth capturing — clarifying mockReturnValueOnce vs
  mockReturnValue in the transaction mock pattern, since this session surfaced a
   3-call where chain not covered by the existing examples:

  Update: .claude/rules/testing-patterns.md

  Why: Existing examples only show 2-call where chains; a 3-call chain (select →
   update-chain → terminate) appears in updateUser combined test and the subtle
  Once vs persistent distinction isn't called out.

   ## Transaction mock — chaining through `.returning()`

   When a transaction has `select` then `update().set().where().returning()`,
  `mockTx.where` must chain back to `mockTx` after the first resolve:

   ```ts
   mockTx.where
     .mockResolvedValueOnce([existingRow])  // 1st call: select terminates
     .mockReturnValue(mockTx);              // 2nd call: update chain →
  .returning()
   mockTx.returning.mockResolvedValueOnce([updatedRow]);
  +When a third where call follows (e.g. a profile table update after a users
  update), use mockReturnValueOnce(mockTx) (not mockReturnValue) for the middle
  call so the default doesn't bleed into the terminating call:
  +
  +```ts
  +mockTx.where
  - .mockResolvedValueOnce([existingRow])  // 1st: select terminates
  - .mockReturnValueOnce(mockTx)           // 2nd: update chain → .returning()
  (Once, not persistent)
  - .mockResolvedValueOnce([]);            // 3rd: second table update
  terminates
  +mockTx.returning.mockResolvedValueOnce([updatedRow]);
  +```

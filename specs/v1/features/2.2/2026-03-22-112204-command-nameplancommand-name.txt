     Task 2.2: Validation Schemas

     Context

     Task 2.2 adds the validation layer for the auth routes. Without it, the
     auth service (Task 2.3) has no input sanitization, and Express routes
     cannot reject malformed requests early. This task creates:
     - A reusable Zod validation middleware factory (validate.ts)
     - Zod schemas for all four auth endpoints (auth.validators.ts)

       password: z.string().min(1),
     });

     export const changePasswordSchema = z.object({
       oldPassword: z.string().min(1),
       newPassword: z.string().min(8).max(128),
     });

     export const resetPasswordSchema = z.object({
       token: z.string().min(1),
       newPassword: z.string().min(8).max(128),
     });

     export type RegisterInput = z.infer<typeof registerSchema>;
     export type LoginInput = z.infer<typeof loginSchema>;
     export type ChangePasswordInput = z.infer<typeof changePasswordSchema>;
     export type ResetPasswordInput = z.infer<typeof resetPasswordSchema>;

     Notes:
     - Zod v4 removed .toLowerCase() — use .transform(v => v.toLowerCase())
     instead
     - loginSchema.password uses min(1) not min(8) — real check is done in the
     service layer

     src/middleware/validate.ts

     import { z } from "zod";
     import type { Request, Response, NextFunction } from "express";
     import { sendError } from "../utils/index.js";

     export function validate(schema: z.ZodTypeAny) {
       return (req: Request, res: Response, next: NextFunction): void => {
         const result = schema.safeParse(req.body);
         if (!result.success) {
           const message = result.error.issues
             .map((issue) => issue.message)
             .join(", ");
           sendError(res, message, 400);
           return;
         }
         req.body = result.data;
         next();
       };
     }

     Key decisions:
     - Use result.error.issues (not .errors — removed in Zod v4)
     - Use z.ZodTypeAny as parameter type
     - Replace req.body with result.data so transforms (e.g., lowercased email)
     propagate downstream
     - Reuse sendError from ../utils/index.js — keeps response envelope
     consistent
     - No asyncHandler needed — safeParse is synchronous

     ---
     Test Cases

     validate.test.ts

     - Valid body → calls next(), replaces req.body with parsed data
     - Invalid body → calls sendError with 400, does NOT call next()
     - Multiple invalid fields → error string contains all issue messages joined
      by ", "
     - Transform applied → coerced data written to req.body (e.g., uppercase
     email lowercased)
     - Optional fields absent → passes through fine
     - Empty body against required schema → 400

     Mock setup (follow async-handler.test.ts pattern):
     mockRes = { status: vi.fn().mockReturnThis(), json: vi.fn() };
     mockNext = vi.fn();

     auth.validators.test.ts

     No mocks needed — Zod is pure. Use schema.safeParse() and assert on
     result.success.

     Per schema key cases:
     - registerSchema: valid full input, valid without optional fields, bad
     email fails, password < 8 fails, password > 128 fails, email lowercased in
     output
     - loginSchema: valid passes, empty password fails, bad email fails
     - changePasswordSchema: valid passes, empty oldPassword fails, short
     newPassword fails
     - resetPasswordSchema: valid passes, empty token fails, short newPassword
     fails
